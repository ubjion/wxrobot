# 资源复用与性能统计设计

## 目标

在不改变回复业务规则、不增加启动预热、不放宽发送安全检查的前提下：

- 复用微信 GUI、联系人名称映射及 HTTP 客户端；
- 按阶段记录最近 50 次耗时；
- 计算 P50/P95 并持久化到本地 JSON；
- 统计失败不能阻塞消息处理或微信发送；
- 指标中不保存用户身份、消息正文、搜索词或 AI 回复。

这两项优化主要改善第二轮及后续请求，并提供定位首轮瓶颈的数据。外部 API 冷启动仍可能使首次请求超过 3～4 秒。

## 范围

### 包含

- `WeChatGUI` 实例健康复用与失效重建；
- 微信用户 ID 到显示名称的 TTL/LRU 缓存；
- DeepSeek、Firecrawl、Open-Meteo HTTP 客户端复用和退出关闭；
- 路由、参考资料、联网、AI、联系人解析、UI 打开、UI 发送、发送确认及总耗时统计；
- 最近 50 条样本的本地 JSON 持久化；
- 每 10 个完整请求输出一次汇总日志。

### 不包含

- UI 启动预热；
- OCR 预热；
- AI 与 UI 并行执行；
- 联网搜索规则调整；
- 模型、提示词或上下文长度调整；
- 流式或分段发送。

## 组件设计

### `PerformanceTracker`

新增 `app/services/performance.py`，负责：

- 使用线程锁保护阶段数据；
- 每个阶段通过 `deque(maxlen=50)` 保存最新样本；
- 启动时从 JSON 加载合法的非负数字；
- 计算 count、P50 和 P95；
- 完整请求结束时一次性原子写入 JSON；
- 每累计 10 个完整请求输出一次汇总日志。

百分位使用 nearest-rank 算法：排序后取 `ceil(p * n) - 1`，空样本不输出百分位。

默认文件位置：

```text
%LOCALAPPDATA%\wx-bot\performance.json
```

可通过 `WX_BOT_PERFORMANCE_FILE` 覆盖。

JSON 结构：

```json
{
  "version": 1,
  "updated_at": "2026-09-23T12:00:00+08:00",
  "phases": {
    "ai_request": [2.1, 1.9, 2.4],
    "ui_send": [0.8, 0.7, 1.0],
    "total": [3.2, 3.0, 3.8]
  },
  "summary": {
    "total": {"count": 3, "p50": 3.2, "p95": 3.8}
  }
}
```

写入流程为“同目录临时文件 → flush/fsync → `os.replace`”，避免中断时留下半个 JSON。

### GUI 复用

`WeChatUISender._get_gui()` 保持单实例缓存。每次复用前调用轻量 `is_alive()`：

- 存活：直接返回；
- 句柄失效或健康检查异常：清空后重建一次；
- 重建失败：抛出原发送异常，不无限重试。

不在程序启动时创建 GUI，不主动打开会话。

### 联系人映射缓存

`WeChatUISender` 内部增加线程安全 TTL/LRU 缓存：

- key：原始微信用户/群 ID；
- value：非空显示名称和写入时间；
- 最大 512 项；
- TTL 10 分钟；
- 命中时跳过数据库 `get_nickname`；
- 查询异常、空值及原 ID 回退结果不缓存；
- 超量时移除最久未使用项。

缓存不写磁盘，避免保存联系人关系。

### HTTP 客户端复用

- `DeepSeekClient`：继续复用构造时创建的 OpenAI 客户端，并增加 `close()`；
- `FirecrawlSearchClient`：继续复用单个 Firecrawl 客户端，若 SDK 提供关闭方法则在退出时调用；
- `OpenMeteoWeatherClient`：改为构造时创建一个长期 HTTP 客户端，所有地理编码和天气请求共用连接池，并提供 `close()`；
- `main()` 在退出路径统一关闭上述客户端；关闭失败只记警告。

不发送额外的模型/API 预热请求。

## 阶段定义

| 阶段 | 起止范围 |
|---|---|
| `message_read` | 单轮数据库新消息读取 |
| `routing` | 消息类型、群聊 @、命令与意图判断 |
| `reference_context` | 本地知识与可选联网参考资料整体构建 |
| `web_search` | Firecrawl 请求本身 |
| `ai_request` | DeepSeek 请求本身 |
| `contact_resolve` | 用户 ID 到显示名称解析 |
| `ui_open_chat` | 定位并打开目标会话 |
| `ui_send` | 输入并触发发送 |
| `send_verify` | 数据库回读确认 |
| `total` | 回调收到事件至自动发送完成或失败 |

阶段可以缺失，例如普通回复没有 `web_search`；统计只针对实际执行的阶段。

## 数据流

1. `main()` 创建一个 `PerformanceTracker` 并注入需要计时的服务。
2. 各服务只调用内存 `record(phase, seconds)`，不在阶段中写磁盘。
3. `BotRuntime.handle_event()` 在 `finally` 中记录 `total`。
4. 一个完整请求结束后调用 `flush()`，一次性更新 JSON。
5. 第 10、20、30…个完整请求完成时记录各阶段 count/P50/P95。

手动确认模式下，`total` 只统计回复生成并进入确认队列的耗时；后续人工发送单独记录 UI 阶段，不将人工等待时间计入系统耗时。

## 错误处理

- JSON 不存在：从空数据开始；
- JSON 损坏、版本不支持或字段非法：记录警告并从空数据开始，不覆盖原损坏文件，直到产生第一批新数据；
- 指标写入失败：记录异常类型，不影响回复；
- GUI 健康检查失败：只重建一次；
- 联系人解析失败：按原 ID 走现有回退，不缓存失败；
- HTTP 客户端关闭失败：记录警告并继续退出。

## 测试与验收

- 同一个 `WeChatUISender` 连续调用只创建一个健康 GUI；失效后仅重建一次；
- 同一联系人 10 分钟内只调用一次名称解析器，过期后重新查询；
- 缓存超过 512 项会淘汰最久未使用项；
- DeepSeek、Firecrawl、天气请求连续调用复用同一客户端；
- 每个阶段最多保留 50 条，重启后继续加载；
- P50/P95 使用指定 nearest-rank 结果；
- JSON 使用原子替换，写入失败不影响业务返回；
- 每 10 个完整请求输出一次汇总；
- JSON 和日志中不出现用户 ID 或消息正文；
- 原有回复、天气、搜索、定时任务和微信发送测试保持通过。
